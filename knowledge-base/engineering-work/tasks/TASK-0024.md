# TASK-0024: Fix publish permission — only tenant owner can publish (413 fallback / 403)

## Parent Feature

- Publishing Pipeline (ADR-010 SDUI Publishing)

## Engineering Specification

- [KB-061 Runtime Update Versioning](../../ARCHITECTURE/KB-061-runtime-update-versioning-architecture.md)
- [api-endpoints-reference.md](../../backend/api-endpoints-reference.md) — `POST /api/v1/merchants/:id/publishing/publish` and `POST /api/v1/merchants/:id/publish`

## Repository Target

- backend/

## Description

Frontend `dukaDesk` calls `POST /api/v1/merchants/:id/publishing/publish` via `PublishingPipeline.js:104` and `PUT /api/v1/merchants/:id/config`. Backend currently enforces `only tenant owner can perform this action` (`tenant.ownerId === user.id`), returning `403` (observed as `413 Request Entity Too Large` when payload large, and as `403` when non-owner). Demo fallback in `api.js:913` exists because backend was unavailable, but live Railway `duka-backend-production.up.railway.app/api/docs` now enforces the check.

Mobile publishing from canvas should succeed for the authenticated merchant owner. One successful push was observed after correct owner, but subsequent attempts as non-owner/member fail. This blocks merchant apps from publishing.

## Acceptance Criteria

- [ ] `POST /api/v1/merchants/:id/publishing/publish` checks `merchant.members` / RBAC, not strict `ownerId === user.id` — allow `tenant_owner` and `admin` roles (or `merchant.ownerId` + `merchant.admins`).
- [ ] `POST /api/v1/merchants/:id/publish` and `PUT /api/v1/merchants/:id/config` same RBAC.
- [ ] Returns `403` with machine-readable `code: "NOT_OWNER"` and human message for frontend to surface friendly toast, not generic 413.
- [ ] Existing demo fallback in `dukaDesk/src/services/api.js` and `PublishingPipeline.js` keeps working when backend returns 403 (local `demoStore` save).
- [ ] Add integration test: owner can publish, member cannot (unless admin), unauthenticated 401.
